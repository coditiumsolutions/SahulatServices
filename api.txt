Local Base URL:    https://localhost:7265/api/
Deployed Base URL:  https://sahulatghartak.com/api/
DB Server: 34.131.41.192,1433
Format: REST over HTTPS, JSON request/response bodies
Auth: None currently — no Authorization header/token required; identity is passed via userId/mobileNo/profileId fields in request bodies

DateTime fields: all DateTime values in API responses are UTC, serialized as ISO-8601 with an
explicit "Z" suffix (e.g. "2026-09-22T11:29:43.137Z") — added 2026-09-23 via a global
UtcDateTimeJsonConverter (previously the "Z" was missing, since EF Core returns SQL Server
datetime columns as Kind=Unspecified). The app is responsible for converting to local/Pakistan
display time; do not assume these are already Pakistan time. Operations are Pakistan-based (PKT,
UTC+5, no DST) — recommended client handling: parse as UTC, then convert to local/PKT for display.

Purpose: Authoritative source of truth for this project's backend API contract.
Read this file before implementing, modifying, or debugging any API integration
in the Flutter app (HTTP calls, request/response models, API service classes).

Deployed:  https://sahulatghartak.com/api/auth/register-client

Request Body:
{
  "mobileNo": "03335191392",
  "password": "ghauri12",
  "confirmPassword": "ghauri12",
  "fullName": "Shahid",
  "gender": "Male"
}

Notes (cnic):
- cnic is OPTIONAL on this endpoint (shipped 2026-09-04) — omit it, or send null/"" and it is
  stored as NULL on Clients. Clients.CNIC is nullable in the DB; nothing else depends on it.
- The Flutter app's placeholder-CNIC workaround (AuthApiService.registerCustomer /
  _randomPlaceholderCnic) is no longer needed and should be removed — stop sending the field.
- A real CNIC is still REQUIRED (and unique) on the provider upgrade flow,
  POST /api/auth/register-provider below.

Success (201):
{
  "success": true,
  "message": "Client registered successfully. Verify OTP to activate your account.",
  "data": {
    "userId": 1,

    "userType": "Client",
    "fullName": "Shahid",
    "mobileNo": "03335191392",
    "categoryId": null,
    "categoryName": null
  }
}

Notes:
- Mobile format: 03XXXXXXXXX
- Account is created with IsVerified=false until OTP is verified
- Recommended flow: register-client -> send-otp (Registration) -> verify-otp -> login

Fail (400):

POST Register Provider (upgrade client to provider)
--------------------------------------------------------------------------------
Local:     https://localhost:7265/api/auth/register-provider
Deployed:  https://sahulatghartak.com/api/auth/register-provider

Request Body (current/legacy app — still fully supported, unchanged, single category):
{
  "mobileNo": "03335191392",
  "password": "ghauri",
  "fullName": "Shahid",
  "cnic": "37405-1234567-1",
  "gender": "Male",
  "experienceYears": 2,
  "description": "Experienced provider",
  "city": "Karachi",
  "categoryId": 1
}

Request Body (new app, optionally registering multiple categories — added 2026-09-21):
{
  "mobileNo": "03335191392",
  "password": "ghauri",
  "fullName": "Shahid",
  "cnic": "37405-1234567-1",
  "gender": "Male",
  "experienceYears": 2,
  "description": "Experienced provider",
  "city": "Karachi",
  "categoryIds": [1, 3],
  "primaryCategoryId": 1
}

Notes:
- Two mutually exclusive ways to specify category, both still supported:
  - legacy: categoryId OR categoryName — single category, becomes the provider's only/primary category
  - new, OPTIONAL (added 2026-09-21): categoryIds (array, at least 1) + primaryCategoryId (must be
    one of categoryIds) — registers the provider with ALL of categoryIds; primaryCategoryId is
    flagged as primary. If categoryIds is present, categoryId/categoryName are ignored.
  - omitting categoryIds entirely (current/legacy app builds) is exactly today's behavior — no
    change in outcome, this is purely additive.
  - TODO(remove after old app retired): once every live app build always sends categoryIds for
    provider registration, categoryId/categoryName can be retired and categoryIds +
    primaryCategoryId made the sole required path. Tracked in docs/flutter-changes.md.
- verifies existing client using mobileNo + password
- client must be OTP-verified (UsersLogin.IsVerified=true) before upgrade
- CNIC must be unique across Providers (DB unique constraint)
- city is optional — must be one of the values returned by GET /api/cities (case-insensitive)
  when provided, else 400; if omitted, falls back to the client's existing City (may be null)

Success (200):
{
  "success": true,
  "message": "Account upgraded to provider successfully.",
  "data": {
    "userId": 1,
    "profileId": 4,
    "providerUid": 4,
    "userType": "Provider",
    "fullName": "Shahid",
    "mobileNo": "03335191392",
    "categoryId": 1,
    "categoryName": "Plumber",
    "categoryIds": [1, 3],
    "clientId": 1,
    "city": "Karachi"
  }
}

Notes (register-provider):
- profileId and providerUid are the same value (Providers.UID)
- clientId is the original Clients.UID — always present, since only an existing client account
  can be upgraded, and the Clients row is kept (not deleted) after upgrade. Use it to submit
  customer service requests (POST /api/customer-service-requests) even after becoming a provider.
- city is Providers.City after the upgrade (see request notes above for validation/fallback)
- categoryIds in the response (added 2026-09-21) lists every category the provider was
  registered with — [categoryId] for a legacy single-category registration
- Document upload is a separate API: POST /api/provider/upload-documents
- Manage additional categories after registration via GET/PUT /api/providers/{providerUid}/categories
  (see PROVIDERS DETAIL APIs section) — no need to re-register to add more later

Fail (401):
{
  "success": false,
  "message": "Invalid mobile number or password.",
  "data": null
}

Fail (403):
{
  "success": false,
  "message": "Mobile number is not verified. Please verify OTP first.",
  "data": null
}

Fail (409):
{
  "success": false,
  "message": "Account is already registered as a provider.",
  "data": null
}

Fail (409 — duplicate CNIC):
{
  "success": false,
  "message": "CNIC is already registered to another provider.",
  "data": null

POST Delete Account
--------------------------------------------------------------------------------
Local:     https://localhost:7265/api/auth/delete-account
Deployed:  https://sahulatghartak.com/api/auth/delete-account

Request Body:
{
  "mobileNo": "03335191392",
  "password": "ghauri12"
}

Success (200):
{
  "success": true,
  "message": "Account deleted successfully.",
  "data": {
    "mobileNo": "03335191392"
  }
}

Fail (400):
{
  "success": false,
  "message": "Mobile number is required.",
  "data": null
}

Fail (401):
{
  "success": false,
  "message": "Invalid mobile number or password.",
  "data": null
}

Fail (404):
{
  "success": false,
  "message": "Account not found.",
  "data": null
}

Notes:
- Permanently and irreversibly deletes the account (Client and/or Provider — a client
  upgraded to provider has both rows deleted/anonymized together, since both are keyed
  off the same UsersLogin). This is NOT a freeze/deactivation. Re-verifies password
  the same way as Login before proceeding.
- Hard-deleted (rows physically removed): ProviderDocuments row + the provider's uploaded
  files under wwwroot/uploads/providers/{ProviderUID}/ (profile photo, CNIC front/back);
  UserOTP rows for this mobile number; ClientAddresses rows that have no
  CustomerServiceRequests referencing them.
- Anonymized (PII scrubbed, row kept because FK-restricted history references it and
  hard-deleting would break other users' booking/financial records): UsersLogin
  (MobileNo -> "deleted-{userId}", PasswordHash randomized, IsActive=false,
  IsVerified=false — mobile number becomes eligible for re-registration since it no
  longer matches the original); Clients (FullName -> "Deleted User {id}", Cnic/Gender
  cleared); Providers (FullName -> "Deleted User {id}", Cnic -> "DEL{id}", Gender/
  Description cleared, IsAvailable=false); any ClientAddresses still referenced by a
  CustomerServiceRequest are left in place (address text only, no direct PII beyond
  what the request itself already retains).
- Untouched (out of scope — belongs to the other party or to platform financial
  records, not solely to this user): CustomerServiceRequests, ServiceBookings,
  PaymentLedger, ProviderPayouts, CommissionRules rows.

POST Reset Password
--------------------------------------------------------------------------------
Local:     https://localhost:7265/api/auth/reset-password
Deployed:  https://sahulatghartak.com/api/auth/reset-password

Request Body:
{
  "mobileNo": "03335191392",
  "otp": "458963",
  "newPassword": "newSecurePass1",
  "confirmNewPassword": "newSecurePass1"
}

Notes:
- Atomic verify-OTP + set-password in a single call (mirrors Delete Account
  re-verifying identity in the same call as the sensitive action) — there is no
  separate "verified" state from a prior call that could be replayed
- Recommended flow: send-otp (otpType=PasswordReset) -> reset-password
- Looks up the latest unverified UserOTP row scoped to this mobileNo AND
  otpType=PasswordReset specifically (does not fall back to the newest
  unverified OTP of any type, unlike generic Verify OTP)
- Max 3 invalid attempts (AttemptCount), 5 minute expiry — same OTP
  infrastructure/limits as Send OTP / Verify OTP
- On success: UserOTP.IsVerified=true, VerifiedOn set; any other pending
  PasswordReset OTPs for this mobile number are invalidated so an old code
  can't be replayed
- Only updates UsersLogin.PasswordHash — does not affect Clients/Providers
  rows, IsVerified, IsActive, or anything else

Success (200):
{
  "success": true,
  "message": "Password reset successfully.",
  "data": {
    "mobileNo": "03335191392"
  }
}

POST Send OTP
--------------------------------------------------------------------------------
Local:     https://localhost:7265/api/auth/send-otp
Deployed:  https://sahulatghartak.com/api/auth/send-otp

Request Body:
{
  "mobileNo": "03001234567",
  "otpType": "Registration"
}

Notes:
- otpType: Registration | Login | PasswordReset
- Mobile format: 03XXXXXXXXX (optional +92 prefix normalized)
- OTP is 6 digits; ExpiryTime = now + 5 minutes
- Unverified OTP for same mobile+type is updated (not duplicated)
- Registration: if mobile already exists and IsVerified=true -> 409
- PasswordReset: opposite check — account must already exist and be a
  verified Client/Provider/Staff (UsersLogin.IsVerified=true), otherwise
  there's nothing to reset -> 404
- data.otp is controlled by config Otp:IncludeInResponse (true = include code; false = null)
- TEMPORARY: IncludeInResponse=true on deployed API until a real SMS gateway is wired; then set false

Success (200 when Otp:IncludeInResponse=true):
{
  "success": true,
  "message": "OTP sent successfully.",
  "data": {
    "mobileNo": "03001234567",
    "otpType": "Registration",
    "expiryTime": "2026-07-20T16:40:00",
    "otp": "458963"
  }
}

Success (200 when Otp:IncludeInResponse=false):
{
  "success": true,

POST Upload Provider Documents
--------------------------------------------------------------------------------
Local:     https://localhost:7265/api/provider/upload-documents
Deployed:  https://sahulatghartak.com/api/provider/upload-documents

Content-Type: multipart/form-data

Form Fields:
- ProviderUID (int, required)
- ProfilePhoto (file, optional*)
- CNICFront (file, optional*)
- CNICBack (file, optional*)
- PoliceVerification (file, optional) [v3.20] — always optional, on both first submission and
  edit. Old app builds never send this field and are unaffected; new app builds may also omit it
  (e.g. a provider hasn't obtained the certificate yet). No isFirstSubmission requirement applies
  to this field, unlike the three above.

* First-time submission (provider has no documents row yet, e.g. during initial
  registration): ProfilePhoto, CNICFront, and CNICBack are required — omitting any of those
  three returns 400. PoliceVerification is never required (see above).
  Edit / replace (provider already has a documents row): send only the file(s)
  that changed. Any field present replaces that stored image (same jpg/jpeg/png,
  5 MB validation, saved as profile.jpg/cnic_front.jpg/cnic_back.jpg/police_verification.jpg).
  Any field omitted leaves the provider's existing stored image for that slot unchanged.
  Re-uploading CNICFront and/or CNICBack resets IsVerified to false until an
  admin re-verifies. Re-uploading ProfilePhoto alone does NOT reset IsVerified
  (validated client-side by face detection at capture, not by manual review).
  Re-uploading PoliceVerification does NOT reset IsVerified either (unrelated to CNIC/provider
  identity verification).

Status (CustomerServiceRequests.Status) — live CHECK:
  Initiated | Assigned | Accepted | In Progress | Completed | Cancelled | Rejected

Local:     https://localhost:7265/api/customer-service-requests
Deployed:  https://sahulatghartak.com/api/customer-service-requests

Optional query: ?clientUid=1

Request Body: none

Notes:
- providerUid, providerName, providerMobileNo, providerProfilePhotoPath, providerCnic are populated
  once a ServiceBooking exists for this request AND that booking's status is Accepted, In Progress,
  Completed, or Closed (same rule as GET /service-bookings). Otherwise (no booking yet, booking still
  Pending, or Rejected) all five fields are null.
- passcode is populated once the linked ServiceBooking has a non-null Passcode — i.e. the booking
  has been Accepted (Passcode is generated at accept time, see POST .../respond in the Service
  Bookings section). If no booking exists yet, or it hasn't been accepted yet, passcode is null.
  This is the only place the completion passcode is exposed — it is deliberately omitted from all
  /service-bookings responses so the provider app cannot read the customer's own verification code.
- cancelReason is the reason the customer gave when they cancelled this request (Status="Cancelled"
  via PUT .../{requestUid}, see below). Null unless the request has been cancelled by the customer.
- IMPORTANT: contactPerson/contactNo are free-text fields captured from the request form at create/
  update time (see POST/PUT below) — they represent who the requester wants contacted on-site for
  THIS specific request, and are NOT guaranteed to match the account holder's own name/number
  (clientName / the client's UsersLogin.MobileNo). A client can book on behalf of someone else, or
  simply type a different contact number. Do not treat contactPerson/contactNo as "the logged-in
  client's identity" in the UI — use clientName (and the client's own profile/account data) for that.
- progressStatus is a COMPUTED, read-only field for the client progress bar — it is never
  persisted and never equals the raw "status" column. Values: "Requested" (request Status=Initiated
  / no non-Rejected booking yet), "Assigned" (booking exists, provider hasn't started), "In Progress"
  (provider is actively on the job — either they tapped Start, or the preferred service date/time has
  arrived while the booking sits Accepted), "Completed" (job done, whether or not staff has since
  closed it out). progressStatus is null whenever the request or its booking is Cancelled — render a
  plain "Cancelled" label and hide the progress bar entirely rather than switching on this field.
  Do not derive UI state from "status" directly for the progress bar; use progressStatus.
  See docs/status-workflow.md for the full design and rationale.

POST Respond To Booking (Provider Accept/Reject)
--------------------------------------------------------------------------------
Local:     https://localhost:7265/api/service-bookings/{bookingUid}/respond
Deployed:  https://sahulatghartak.com/api/service-bookings/{bookingUid}/respond

Example:
POST https://localhost:7265/api/service-bookings/1/respond

Request Body (accept):
{
  "providerUid": 4,
  "accept": true
}

Request Body (reject):
{
  "providerUid": 4,
  "accept": false,
  "reason": "Too far from my service area"
}

Notes:
- booking must belong to providerUid and currently be Status="Pending" (i.e. staff-assigned,
  awaiting provider response)
- FIRST-ACCEPT-WINS: when a request is fanned out to multiple providers (multiple sibling
  ServiceBookings rows, same RequestUid, all Status="Pending"), the first provider to call
  accept:true atomically claims the job. All other sibling Pending bookings for that
  RequestUid are immediately auto-superseded: Status="Cancelled",
  CancelReason="Assigned to another provider". They will no longer appear in that provider's
  GET /api/service-bookings?providerUid= list. The claim is race-safe (atomic conditional
  DB update) — if two providers accept at nearly the same instant, exactly one succeeds.
- accept:true -> Status="Accepted", AcceptedOn set, a 4-digit Passcode is generated
  server-side. It is NOT returned in this (or any) /service-bookings response — see
  GET /customer-service-requests below for the client-facing passcode field
- accept:true is IDEMPOTENT for the winning provider: calling it again on a booking this same
  provider already accepted (Status="Accepted"/"In Progress"/"Completed"/"Closed") returns
  200 success again rather than an error (message: "Booking accepted successfully.").
- accept:true on a booking already lost to another provider (Status="Cancelled" via the
  supersede path above, or otherwise no longer Pending) returns 400 with message
  "This job has already been assigned to another provider." — treat this as an expected,
  non-generic failure case; the app should refresh its pending-jobs list on receiving it.
- accept:false -> reason is REQUIRED (non-empty), fails with 400 if missing/empty.
  Status="Rejected" (staff-only; hidden from all client/provider-facing GET/list responses),
  reason is persisted to RejectReason. The parent CustomerServiceRequest reverts to
  Status="Initiated" (so staff can reassign) ONLY if this was the last remaining Pending
  sibling booking for that request; if other providers are still Pending on the same
  request, the request stays Status="Assigned" so they can still respond.

PUT Update Provider Location (REST fallback for live push)
--------------------------------------------------------------------------------
Local:     https://localhost:7265/api/provider-locations/{providerUid}
Deployed:  https://sahulatghartak.com/api/provider-locations/{providerUid}

Auth: Bearer JWT required — caller must be the provider identified by {providerUid}.

Notes:
- Primary real-time path is the SignalR hub's PushLocation method (see below). This REST endpoint
  is a fallback for clients that cannot hold a persistent WebSocket connection.
- Idempotent: ClientTimestampUtc (device GPS-fix time) drives an ordering guard — a request whose
  timestamp is not strictly newer than the currently stored LocationUpdatedOn is silently ignored
  (still returns 200, with "applied": false), so retries and out-of-order/delayed calls can never
  regress the stored position. This guard is shared with the Hub's PushLocation, so pushing via
  both transports for the same provider is safe.
- If bookingUid is supplied and the update was applied, also broadcasts to that booking's SignalR
  group ("booking-{bookingUid}"), same event shape as the Hub's LocationUpdated event.

Example:
PUT https://localhost:7265/api/provider-locations/5

Request Body:
{
  "clientTimestampUtc": "2026-08-24T10:15:30Z",
  "latitude": 31.5210,
  "longitude": 74.3590,
  "bookingUid": 42
}

Success (200):
{
  "success": true,
  "message": "Location updated successfully.",
  "data": {
    "latitude": 31.5210,
    "longitude": 74.3590,
    "locationUpdatedOn": "2026-08-24T10:15:30Z",
    "applied": true
  }
}

Success — stale/duplicate update ignored (200):
{
  "success": true,
  "message": "Update ignored: a newer location is already stored.",
  "data": {
    "latitude": 31.5210,
    "longitude": 74.3590,
    "locationUpdatedOn": null,
    "applied": false
  }
}

Fail (403): caller's JWT does not resolve to this providerUid
Fail (400):
{
  "success": false,
  "message": "clientTimestampUtc is too far from server time.",
  "data": null
}

--------------------------------------------------------------------------------
SignalR Hub: Live Location Tracking
--------------------------------------------------------------------------------
Local:     wss://localhost:7265/hubs/location
Deployed:  wss://sahulatghartak.com/hubs/location

Auth: JWT Bearer required. WebSocket clients cannot set the Authorization header on the handshake,
so pass the token via query string instead: /hubs/location?access_token={jwt}
(the JavaScript SignalR client's accessTokenFactory option does this automatically.)

Hub methods (client invokes):
- JoinBookingGroup(bookingUid: int) — subscribe to a booking's live location stream. Safe to call
  repeatedly (idempotent — SignalR no-ops if already a member). Must be re-invoked after any
  reconnect, since group membership does not survive a new ConnectionId.
- LeaveBookingGroup(bookingUid: int) — unsubscribe.
- PushLocation(bookingUid: int, latitude: decimal, longitude: decimal, clientTimestampUtc: DateTime)
  — provider-only. Caller's JWT must resolve to the Provider that owns bookingUid, or the hub
  throws. Writes through the same idempotent guard as the REST PUT fallback above — a duplicate or
  out-of-order call is a safe no-op and does not re-broadcast.

Server event (client listens for):
- LocationUpdated — payload: { bookingUid, latitude, longitude, timestamp }, sent to the
  "booking-{bookingUid}" group whenever a PushLocation (or REST PUT with bookingUid) call actually
  applies a new position.

Example (JS):
const connection = new signalR.HubConnectionBuilder()
  .withUrl("/hubs/location", { accessTokenFactory: () => jwtToken })
  .withAutomaticReconnect()
  .build();
connection.on("LocationUpdated", data => { /* move marker */ });
await connection.start();
await connection.invoke("JoinBookingGroup", bookingUid);
